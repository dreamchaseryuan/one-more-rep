## 测试（已完成）

`npm test` 跑 94 个用例，全是纯函数，约 400ms。挂在 CI 的 `npm run build` 之前，
且在拉媒体之前（测试几百毫秒，媒体 130 MB，顺序反了会白拉一遍才失败）。

覆盖的是**已经踩过的那几个 bug**，不是泛泛的「提高质量」——它们形状完全一样：
出在纯函数里、不报错、只是安静地算错。

| 测试文件 | 守着什么 |
|---|---|
| `date.test.ts` | 时区。**同时是时区钉死的守卫**（见下） |
| `useWorkouts.test.ts` | `touched`：计划预填 ≠ 实际做了；容量只算实际做的组 |
| `programs.test.ts` | 轮转按**名字**推导、递增组的算术与几个不变量 |
| `id.test.ts` | 非安全上下文下 id 不抛异常、形状仍是合法 v4 |
| `backup.test.ts` | 坏输入不污染好数据、v1→v4 四个版本都能读进来 |
| `usePersist.test.ts` | 合并多次改动、flush 后不重复写、无待写内容时 flush 是空操作 |
| `data.test.ts` | `mediaUrl` **任何情况下都不返回外部地址** |
| `recommend.test.ts` | 推荐器的每条规则，以及「每个目标都真的改变输出」——**三个目标 × 2/3/4/5/6 天 × 40/60/90 分钟**全跑一遍 |

**一处必须知道的机关**：`vitest.config.ts` 顶层把 `process.env.TZ` 钉成 `Asia/Shanghai`。
不钉的话 CI 跑在 UTC 上，`toISOString()` 恰好等于本地日期，时区用例会**假通过**——
而那正是它要防的那个 bug。`date.test.ts` 里第一条断言同时在守着这个钉死有没有被删掉。

已做变异测试验证：把配置改成 UTC，该断言确实失败（不是摆设）。

## 可以做

### 1. 加重建议的三个查询建索引

`lastPerformance` / `bestSet` / `weightHistory` 都是 O(历史条数)，且会在 `WorkoutPanel` 里**按动作各调一遍**。
按 `history` 变化一次性建 `Map<exerciseId, ...>`。数据量大了才明显。

### 2. `BASE` 改成环境变量

`vite.config.ts` 写死 `/fitness-app/`，仓库改名就全站 404。
改 `process.env.BASE_PATH ?? '/fitness-app/'`，CI 里传。

### 3. CI 不拉 GIF

`deploy.yml` 里的 `media:fetch-videos` 会拉 122 MB，`dist` 因此是 140 MB。
GIF 是可选依赖（README「已知取舍」里写了），去掉这一步产物降到 18 MB 左右，
部署和移动端首次加载都受益。代价：线上详情页只有静态图。

### 4. 监听 `storage` 事件

两个标签页同时开着会互相覆盖（后写的赢）。个人自用影响小，优先级低。

### 5. 挡住「界面里的 markdown 星号」

`**重点**` 写进会渲染的字符串里，出来的是两个星号，不是粗体。**已经犯过四次**
（两次在 JSX，两次在模板字符串），每次都是看截图才发现的。

正经的守卫要用 TypeScript 的 AST：注释不是 AST 节点，所以走一遍 AST 只找
字符串字面量、模板串和 JSX 文本，就能把「注释里的 `**重点**`」（共 51 处，全都无害）
和「真会渲染的」分开。试过用正则做，误报 51 条，不可用。

三十来行代码，挡的是一个纯外观问题 —— 所以优先级低。但复发率是实打实的。

### 6. 升级 CI 里的 action 大版本

构建时有告警：`actions/checkout@v4` 等被强制跑在 Node 24 上。不影响功能。

## 要先想清楚，不是技术问题

### 多设备数据同步

**打开**在多个设备上早就没问题了——它是个网站。但**数据**不跟着走：
localStorage 是按「浏览器 + 源 + 设备」隔离的，而且 Chrome 的账号同步**不覆盖** localStorage。

三条路：

| | 做法 | 代价 |
|---|---|---|
| A | 就只用手机，电脑上当成独立副本 | 零成本，但两边会分叉 |
| B | 手动导出 JSON → 传给自己 → 导入 | 零开发，适合偶尔切换 |
| C | 做云同步（复用 GitHub 账号，用私有 Gist 当存储） | 要开发，还要处理 token 存放和「两边都改了怎么办」 |

**建议先用 A 或 B 跑一段时间再决定。** C 引入的东西比看上去多，而多设备切换的真实频率
只有用过才知道；现在设计冲突合并策略是凭空猜。**饮食模块的教训就是「设计完了但没人用过」。**

## 明确不做

- **饮食模块**（2026-10-11 决定）。设计文档保留在 [plan-nutrition.md](plan-nutrition.md)，
  但那是**记录，不是待办**。重开之前先读那份文件开头。

- **从力量库里拼一份「女生计划」**（2026-10-11 决定）。
  起因是「女生不一定全是力量训练」——这个观察是对的，但结论不是加一份女生计划：

  1. **那是刻板印象的另一个方向。** 想练力量的女生和想减脂的男生都存在，
     按性别分发计划是在用一个更粗的假设盖住一个更细的问题。
  2. **库撑不起来。** 1324 个动作里 1295 个是按肌群切的力量动作，有氧只有 29 个，
     瑜伽 / 普拉提 / 拉伸体系 0 个。这是 © Gym visual 的健美动作库，
     不是设计没做到 —— 是素材就没有。
  3. **拼计划是教练知识。** 和「不做自动替代推荐」「不做自动替换动作」同一条规矩：
     凭几个选项猜出来的编排，使用者会信，信错了比不给更糟。

  **实际做的是让目标维度变得诚实**：加了「塑形 / 减脂」一个选项，它真的会改变输出
  （次数区间整体上移 + 训练日末尾挂一个自重有氧），并且在结果里明说
  「这仍然是一份力量计划」。不包装成它做不到的东西。

  **如果将来真想覆盖非力量训练**，先解决的是**动作库**，不是推荐器 ——
  需要另一个数据源（瑜伽/普拉提/有氧操），那是 `scripts/build-data.mjs` 那一层的事。
