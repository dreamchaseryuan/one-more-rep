# 饮食模块设计方案

> **状态：设计完成，尚未开工。**
>
> 2026-10-11 搁置。下面的内容来自一轮完整的质问，可作实现依据，但有**一处没定**：
> 第四节的「记录交互」始终没被确认过。开工前必须先定它——它决定那个模块会不会被日常使用，
> 定错了 4c 整段要重写。
>
> 另外第三节的份量策略（不预置我猜的份量）是刻意的取舍，不是遗漏，理由见 ADR 0003。

本文件是设计与实现依据。术语以 `CONTEXT.md` 为准，已定的决定见 `docs/adr/`。

## 一、结论先行

用真实场景实测过（米饭 / 鸡腿 / 蛋白粉 / 食堂菜），**成分表 4 样里 0 样能直接用**。
所以本模块的中心是**使用者自己拥有的食物条目**，成分表退居为查询与参考来源。

这与动作库的做法**正好相反**：动作库是拿来就能用的大数据集，食物没有这样的福气。

## 二、数据源与它的坑

种子：`Sanotsu/china-food-composition-data`（《中国食物成分表标准版第6版》）
1677 条 × 35 字段，per 100g。理由与四个必须记住的坑见 [ADR 0003](./adr/0003-china-food-composition-as-seed.md)。

实现时必须处理的四条：

| 坑 | 处理方式 |
|---|---|
| 生重 / 熟重不分（面条差 2.8 倍） | 列表里**强制区分生熟**，熟食优先排序，生食标注「生，需自行称重」 |
| 蛋白粉那条是错的（50% vs 典型 75%） | 标「参考值存疑」并引导自建；**不静默使用** |
| 有无菜品、份量、鸡皮 | 由使用者自建覆盖，不做自动推算 |
| 数据由 LLM 从截图提取 | 每条都标「参考值」，允许一键修正并记住修正 |

## 三、数据结构

```ts
/** 计量单位。一等公民，不是附属信息。 */
interface Portion {
  label: string;          // "1 碗" / "1 个" / "1 勺"
  grams: number;          // 200
}

interface FoodEntry {
  id: string;
  name: string;                           // "沙县去皮鸡腿"
  portion: Portion;                       // 必填
  per100g: {
    kcal: number;
    protein: number;                      // 必填
    fat?: number;                         // 选填
    carb?: number;                        // 选填
  };
  source: 'cnf' | 'label' | 'estimate';    // 查表 / 抄包装营养成分表 / 自己估
  cnfCode?: string;                        // source='cnf' 时指向成分表
  note?: string;                           // "沙县这个带卤汁，钠高"
}

/** 一次进食记录 */
interface MealEntry {
  id: string;
  date: string;                            // YYYY-MM-DD
  meal: 'breakfast' | 'lunch' | 'dinner' | 'snack' | 'postWorkout';
  foodId: string;
  portions: number;                        // 几份，2 表示两个鸡腿
}
```

**只有 kcal 和 protein 必填**。脂肪碳水选填——强迫填全部，代价是使用者不会去建条目，
而条目数是这个模块成败的唯一指标。

## 四、记录交互

目标：**一顿饭 4 次点击，不打字**。

```
「加食物」→ 搜"米饭" → 点条目（默认 1 碗）→ 记好
            搜"沙县" → 点条目（默认 1 个）→ 点 + 变 2 个 → 记好
```

规则：
- 点条目 = 按默认 Portion 记一份
- 改数量用 +/− 按钮，**不打字**
- 首次记录某个食物时问一次份量（"你这碗大概多少克？"），给常见范围提示，记住
- 想精确到克时可切到克数输入

## 五、饮食目标

**公式给初值，全部可手改，改过之后不再自动覆盖。**

- BMR：Mifflin-St Jeor
- TDEE = BMR × 活动系数
- 总热量：增肌 +300 kcal / 减脂 −400 kcal / 维持 ±0
- 蛋白：1.8~2.2 g/kg 体重（增肌取高、减脂取更高）
- 脂肪：0.8~1.0 g/kg
- 碳水：剩余热量

**TrainingDay / RestDay 两套数字**，差异在碳水与总热量（训练日碳水更高）。
蛋白两套相同——蛋白不随训练日浮动。

身体数据：体重、身高、年龄、性别、活动量。体重按日期记录，TDEE 用**最近一次**体重。

## 六、TrainingDay 判定

**按计划预告**：计划的轮转说今天该练哪个 ProgramDay → 今天就是 TrainingDay。
**+ 手动覆盖**："今天不练了" → 切成 RestDay。

为什么不能按「实际练了没」判定：早上记早餐时就需要知道今天的目标（因为你正在决定吃什么），
而那时训练还没发生。按实际判定会让目标在中途变化，当天数字无法修正。详见对话记录。

## 七、与训练的联动

- 饮食页显示今天是 TrainingDay / RestDay，以及计划让今天练哪个 ProgramDay
- 练后那一餐标 `postWorkout`，并提示蛋白是否吃够（这是最常见的真实缺失）
- 训练与饮食共用一个日期模型，同一天的 Workout 和 MealEntry 可互相跳转

## 八、主动不做的事（附理由）

| 不做 | 理由 |
|---|---|
| 精确碳水循环、营养时机（"练前 90 分钟吃 X 克"）、按训练容量动态调热量 | 最后 10% 的收益、最高的复杂度。总热量和总蛋白占九成效果 |
| 预置我猜的份量（"1 碗 = 200g"）与菜品配方 | 错误的默认值会被反复使用且未必被发现。和蛋白粉那条教训一致 |
| 自动推荐替代食物 / 菜品映射表 | 猜错比不给更糟，使用者会信它 |
| 扫码（Open Food Facts） | 中文覆盖差，收益低于成本 |
| 强制精确到克 | 使用者会因此不用它。**记漏一天的数据比碳水算错 20% 的损失大** |

## 九、待建的脚本与校验

- `scripts/fetch-food.mjs`：拉取成分表 CSV，裁剪成前端用的精简食物数据
- `scripts/build-food.mjs`：清洗 + 生成 `public/data/foods.json`
  - 必须做的清洗：标注生/熟（从 `foodName` 里的「生」「熟」「蒸」「煮」识别）
  - 必须做的标记：蛋白粉那条标 `suspect`
- `scripts/check-foods.mjs`：校验产出（条数、必填字段、生熟标注覆盖率、可疑条目清单）
